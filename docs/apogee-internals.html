Apogee Internals

How a CSV file that KovaaK's writes to disk becomes a rating change on a competitive ladder, and why each part works the way it does.

170 files 57,230 lines 26 validation suites 14 edge functions 12,080 runs uploaded

What Apogee is

One sentence: ranked matchmaking for aim, played inside KovaaK's.

Apogee is not an aim trainer. KovaaK's owns that space and there is no reason to compete with it. Apogee is a layer on top that supplies the one thing solo benchmark grinding cannot: an opponent.

The player never leaves their routine. They queue for a category, Apogee names three scenarios, they alt-tab to KovaaK's and play them exactly as they always would. Apogee watches the stats folder, picks the runs up, verifies them, settles the match and moves the rating. No score entry, no screenshots, no honour system.

Why this shape

Everything else in the space is read-only. evxl shows you a number. KovaaK's leaderboards tell you that you are #4,182 of 58,017, which means nothing emotionally. Voltaic defines a standard, not a game. Nobody owns matched competitive aim; that is the opening.

The spine

A run's journey, end to end. Almost every file in the project is a step on it.

From keypress to rating change 9 steps
1
KovaaK's writes a CSV
…/FPSAimTrainer/stats/<Scenario> - Challenge - <date> Stats.csv

Written progressively as the run ends. Contains per-kill rows, a weapon block, and a key/value tail with Score:, Hash: and Challenge Start:.

2
The watcher notices
src/app/watcher.ts

Waits for the file's size to stop changing before reading. Parsing on the first filesystem event yields a truncated file with no Score: line, which is the classic way to get this wrong.

3
The parser reads it
src/core/stats/parseStatsFile.ts

Never throws. A crash mid-run leaves a partial CSV, and a watcher that dies on one bad file is useless. Validated against all 11,058 files in the corpus: 100% parsed, zero exceptions.

4
If it belongs to a match, it uploads itself
src/app/main.ts → supabase/functions/submit-run

The whole CSV goes to the server, not a summary. That way the integrity checks run over the file as KovaaK's wrote it, and a client cannot present tidy numbers contradicting rows it never sent.

5
The server verifies it, twice
src/core/verify/consistency.ts + kovaaksClient.ts

Local integrity (does the file agree with itself?) and a cross-check against KovaaK's own servers (did this run actually happen?). The run comes out labelled verified consistent suspect or rejected.

6
Your baseline is recomputed
src/core/history/baseline.ts

The number every match is scored against. Always derived from stored runs on the server, never taken from the client.

7
When all three land, the match settles
supabase/functions/settle-match

Deltas recomputed from stored rows, compared against the opponent's frozen deltas, verdict decided. Idempotent: calling twice cannot apply the rating change twice.

8
Glicko-2 moves your rating
src/core/rating/glicko2.ts

Damped by a weight if either side used a provisional baseline, so a noisy match still counts but moves the ladder less.

9
Quests measured, XP lands
src/core/quests/board.ts

The day's board is issued once, from the history before midnight, and measures only runs played since, so a finished quest stays on it. Progress is read from the stats folder rather than counted as events, so a completion cannot be lost by the app being closed at the wrong moment.

Five concepts

The rest of the codebase reads easily once these are clear. Every number below is from the real corpus.

1. Baseline — what you normally score

Definition src/core/history/baseline.ts 
baseline = max( median(last 50 runs),  0.9 × verified personal best )

A median, not a mean, because it ignores outliers in both directions: one disastrous run does not drag it down, one lucky run does not inflate it. The floor at 90% of the player's KovaaK's-verified PB is what stops sandbagging: nobody can claim a baseline far below what KovaaK's itself vouches they can do.

Corrected by measurement

The first version used the mean of the best 30% of recent runs, for sandbag resistance. Measured across 156 scenarios of real history it was badly off-centre: only 26% of genuine runs landed above their own baseline, so matches were decided by who avoided a disaster rather than who played well. The PB floor turned out to be doing the anti-sandbag work, not the high-water statistic — so the statistic could be swapped for a centred one at almost no cost.

2. Delta — how you did today

Definition src/core/match/settle.ts 
delta      = (score − baseline) / baseline
matchScore = mean(delta₁, delta₂, delta₃)     higher wins

Normalising against each player's own baseline is what lets any two players have a real contest. The question stops being "who has more hours on this scenario" and becomes "who showed up sharper today".

The cost, and it is real

You can score higher and still lose. That is intended, and it reads as broken unless it is explained the moment it happens. Every result screen shows raw scores, baselines and deltas together, and explainVerdict() names the case in words when it occurs.

3. Energy — how a season ranks

Reverse-engineered from KovaaK's own API and then validated against real accounts: computed category and overall progress match the server to within 0.005 energy across 20 checks.

The rule src/core/benchmarks/energy.ts 
threshold i is worth   2500 × (i + 1)   energy
between thresholds     linear interpolation
below the first        scales from zero
above the last         caps

category energy  = sum of its scenarios
category rank    = highest category threshold met

The subtlety: per-scenario energy is on a universal scale, but category thresholds differ — Switching demands more energy for the same rank than Clicking does. Getting that backwards is the easy mistake, and it is the reason the two numbers are stored separately.

4. Floor — what you can do reliably

Definition src/core/consistency/floor.ts 
floor   = worst of your last 5 runs
ceiling = your best ever          ← what every benchmark ranks
gap     = (ceiling − floor) / ceiling

The floor is fed through the same energy engine as the ceiling, so "Diamond ceiling, Platinum floor" is a literal statement rather than a metaphor. Only the score going in differs.

5. Verification tier — how much a run is trusted

Why suspect is not rejected

The original design auto-voided anything above the player's PB with no server record. Testing that against real data showed it would produce false positives: 16 of 18 local bests matched KovaaK's exactly, but two did not, and both runs were genuine. Roughly 1 in 9 real personal bests never reaches KovaaK's servers — offline play, a crash, a failed submit. A rule that voids matches on that basis punishes honest players at a rate no ladder survives.

Seasons

A season is the answer to "what does a rank mean". It owns the pool, the thresholds and the ladders, it is frozen once published, and it is the reason nothing here depends on Voltaic any more.

Everything that grades a score used to read data/benchmarks/voltaic-s5.json directly, which made Voltaic the authority on what a rank meant — and put the definition on somebody else's release schedule. A season replaces that. Same numbers to begin with, but ours.

What a season contains data/seasons/season-1.json 
name, status          draft | published | archived
rankNames/Colors      the overall ladder
categories[]          the six: two clicking, two tracking, two switching
  bands[]               one per window, each graded on its own
    window                which window it grades
    rankNames/Colors      that band's own four ranks
    rankMaxes             energy needed per rank in that band
  rankNames/Colors      the chained ladder, kept for the overall readout
  rankMaxes             energy needed per rank in that category
scenarios[]           the pool
  scenario, category    which ladder grades it
  label                 short display name
  rankMaxes             score needed per rank

Six ladders, not one

Each category names and colours its own ranks. The claims are separate — being near the top of Precise Tracking says nothing about Static Clicking — and a shared vocabulary would quietly imply otherwise. They can be different depths: one category can have six ranks where another has four.

Three was the original shape, and it weighted the pool by accident. Category energy is the sum of its families, so a hand-built Clicking section that grew to eleven families while Switching sat at five counted for more than twice as much towards the overall. Splitting each aim type along the sub-skill lines the corpus already names — static against dynamic, precise against reactive, speed against evasive — gives six categories that can each be brought to the same depth, and equal depth is equal weight by construction.

Watch for Everything is keyed to a ladder's length. A category with four ranks has four energy thresholds, and every scenario in it has four score thresholds. Adding a rank name alone breaks the season with an error about a scenario nobody touched, which is why the editor moves all three arrays together and validateSeason refuses a mismatch before anything is written.

A band is a whole benchmark

Each category is cut into four bands — Novice, Intermediate, Advanced, Expert — and each band is graded entirely on its own: its own scenarios, its own four ranks, its own top. A player holds a rank in every band they have played, and nothing asks whether Advanced's first rank is above Novice's last.

They used to chain into one sixteen-rank ladder. That survived while every threshold came from one percentile curve, which descends by construction, and it did not survive adopting the numbers the benchmark authors publish: 59 ranks came out unreachable, 58 of them at a window handover. The cause is not that authors calibrate differently — of those 58, twenty-nine were handovers sharing an author and twenty-nine were not — but that a benchmark's tiers are not rungs. Voltaic Novice and Voltaic Advanced are separate benchmarks, and nobody meant one's first rank to outrank the other's last on a different scenario.

Three states, never two A band with no runs is unmeasured; a band with runs but under its first threshold is measured and unranked; the rest hold a rank. Anything drawing the first two alike tells a player they are bad at Expert when they have never launched it.

seasonAsDifficulties hands each band to the grading engine separately, and there is no new arithmetic behind it: evaluateCategory already treats a flat ladder as the degenerate windowed one, so a band inherits every check validate:engine makes against KovaaK's own numbers.

The overall rank is derived

It is not graded on its own. Each category is reduced to its standing — how far along its own ladder you are, as a fraction — and the overall is where the average of those falls on the overall ladder. Ladders of different depths compare correctly because nothing is compared until it is already a fraction.

The average, not the weakest. Being carried by one strong category is a real thing this says about somebody, and a mean says it. A minimum would make the overall a second, harsher name for the weakest category, which the weakness map already reports and reports better.

Only for seasons A KovaaK's benchmark has one ladder for all its categories, and its overall rank is whatever their servers report. validate:engine holds this code to matching that, so the benchmark path follows the server exactly and the derived path is taken only when a category carries its own ladder.

Why published means frozen

A threshold edit is not like other edits. Raise a rank and everybody who held it yesterday is something else today, with no run played and nothing in their history to explain it. So the editable thing is a draft, and publishing is one-way.

That is enforced by a database trigger rather than by application code, because a guarantee this load-bearing should hold for the data rather than for one path into it. Archiving stays allowed: retiring a season changes which one is current without changing what any past rank meant.

Where season 1's numbers come from

Later seasons derive their thresholds from the previous season's population, which is the whole point — a rank becomes a percentile of what people actually score and never needs maintaining. Season 1 cannot, because there is no population yet.

Its scenarios are Apogee's own — 41 families at four bands, 164 files — so there are no KovaaK's boards to read either. (A first draft was built from other authors' scenarios, with thresholds cut from their boards; it was replaced before anyone played it, and is in git history.) Each is built by editing a real KovaaK's file (src/core/scenario/forge.ts), and its board is predicted: a model fitted on every local scenario that has both a file and a sampled board turns what the file says — target size and speed as angles, the Fitts difficulty of the flick, time to kill — into the board it expects, and the thresholds are read off that at the percentile ladder in data/pool.json. Every threshold carries the model's error in its source, and every one is a seed: once Apogee players have played a scenario, its thresholds should come from them.

npm run build:season builds the files and the season; npm run validate:season-files holds it to its rules, including that every spawn admits its targets and every value lies within what real scenario files use. The research behind the design is docs/season-1-research.md.

The files exist nowhere but in this app, so the client installs them into KovaaK's on launch and rewrites any that differ (src/core/season/installScenarios.ts). Byte for byte, because KovaaK's writes the MD5 of the scenario file into every stats file, and submit-run refuses a run on an Apogee scenario whose hash is not the committed file's — an edited copy under the same name. sync:reference sends the hashes; verify:deployment checks the live ones match.

Past the top of the ladder

A rank is a band and a band has a top, so the ladder stops measuring on purpose. The apex board is the standing that does not.

Scenario energy caps at the last threshold. Two players who have both cleared the hardest rank therefore hold identical energy however far apart they are — which is the honest thing for a rank to do, and leaves the group most likely to keep playing with nothing left to move.

The obvious fix invents a number: keep interpolating past the last threshold and the slope up there is a guess nothing checks. So the apex board is a second standing rather than a longer ladder. It reads the same KovaaK's boards the thresholds were cut from, and it never caps:

Apex points-log10 of your fraction from the top
top 10%    1.0        top 0.1%    3.0
top 1%     2.0        top 0.01%   4.0

A whole point always means ten times fewer people above you, which is the same achievement wherever on the scale it falls. It is defined all the way down the board too, so this is one standing everybody has rather than a second ladder that unlocks at the top.

Percentiles run out exactly where this is needed

The sampled distributions stop at the top 0.1%, and the ladder's own hardest rank is already the top 0.8% — so the range a post-rank board exists to separate sits inside the clamp, where every score reads the same. Sampling finer fractions does not help: a fraction gets coarser in players exactly where the board gets sparser, and 0.0001 of a ten-thousand-entry board is one person.

So the top of each board is sampled in ranks instead — the score at board positions 1, 2, 3, 5, 10, 25, 50, 100, 250, 500. A rank means the same thing on a board of any size, which is what a fraction stops doing up there, and rank 500 sits below the 0.1% point on every board in the pool, so the two samplings overlap rather than leaving a gap between them.

Two things it got wrong first

The handover had to be floored. The two samplings disagree by up to 0.247% where they meet, because the fractional points interpolate linearly across a convex curve. Left alone that is exploitable: where the distribution read better than rank 500, a player could have gained standing by scoring less. Below the last anchor the answer is now floored at it.

A family is graded on its hardest variant only, never the best of them. The ladder's best-of rule is right for a rank and would pay for playing down here, because a percentile is a percentile of whoever played that scenario and an easy board is enormous and mostly people who opened it once. Measured: on 26 of the 43 variant pairs in the corpus where one player has a score on both, the easier scenario pays more.

Why the server computes it

The public board is written from KovaaK's-verified personal bests, not from uploaded runs. A leaderboard with no ceiling is exactly the surface somebody would forge a score onto, and unlike the ladder it is not bounded by thresholds or settled against a baseline. Clients hold no write grant on it, the same rule ratings and verified_pbs already live under.

Nothing here feeds ratings, matchmaking or settlement — the same separation thresholds already have. The client renders its own copy from the committed samplings so the screen works with no session and no network, and where the two disagree the server's is the one that counts.

A leaderboard is public; the table is not

The cross-player board looks like the one place a plain select would do. It is not, and the reason is a bug this project already had once.

Player profiles were world-readable at first — for select using (true) — which let any anonymous caller enumerate the whole player base and join every account to its real Steam profile. The policy that replaced it drew a rule rather than patching a hole: anything a client sees about another player is a decision the server makes. Opponent names already work that way, reaching the client through find-match, which joins with the service role and returns the name in its response.

The standings table shipped world-readable anyway, on the reasoning that a leaderboard is public by definition. True of the board and false of the table: it would have handed out an ordered list of every player_id and their activity to anyone with a session — the same enumeration in weaker clothing. So the table is read-self like verified_pbs, and the board is served by a function that returns a display name, a standing and a position, and no identifier at all. There is nothing in the response to correlate against anything; the caller finds itself by a flag on its own row.

Absent is not zero

A player with no verified best on any graded scenario gets no row, and neither does a category they have not scored in. The first version wrote rows unconditionally, and since the client refreshes whenever the screen opens, everybody who so much as looked at the board landed on it at 0.00 points. That made population a count of people who had opened a screen rather than people with a standing, which turned “you are #47 of 300” into a sentence about nothing.

Ranking is the ordinary competition kind — how many are strictly above you, plus one — so two players tied at the top are both first and the next is third. That is asserted against a real Postgres rather than left as a convention, because dense ranking is the plausible thing for somebody to “fix” it into, and it would quietly tell the second of two tied players they were second.

The life of a match

Five states, and most of the interesting behaviour is in what happens when a match does not finish cleanly.

Statesmatches.status
awaiting_runs   handed out; the clock is running
settled         scored, rating applied
void            ended with nothing rated

An empty pool still gives you a match

Queueing with nobody to play returns a seeding match: the same three seeded scenarios, no opponent, nothing rated. The run set is scored and stored, and that is what the next player is matched against. Without it the pool could never receive its first entry, which on an async-first ladder is the difference between a cold start and no start.

In the UI A seeding match has no verdict. It reads Run set recorded, not a win or a loss, and its rounds read recorded rather than won — a missing opponent delta is null, which is not the same as an opponent who scored exactly their baseline.

A duel is a seeding match with a name on it

Duels add no state to the table above. The challenger plays the seeding match just described; accepting builds the ordinary contested match, with the opponent pinned by id rather than picked by rating proximity. Submission, verification, forfeit, the clock and settlement run on the existing paths unchanged, so a settled duel is indistinguishable from a settled queue match afterwards.

The scenarios, category and window are copied off the challenger's match rather than selected again. That makes “both sides played the same three” structural instead of reconstructed: one row says what the three were, and answer-duel reads it.

What the answerer cannot see How the challenger did. The score is never copied onto the duels row; it lives on the challenger's side of their own match, where the answerer has no side and therefore no read. An answerer who could see it before deciding would be cherry-picking, the same thing the one-match-at-a-time rule stops, pointed the other way.

Statesduels.status
open        sent; the challenger has played, nobody has answered
accepted    answer_match_id points at the contested match
declined    answered, nothing rated
cancelled   taken back by the sender
expired     seven days passed with no answer

answer_match_id is null until the accept, which makes it the repair flag as well as the link: a row reading accepted with nothing in it is a function that died between the two writes. answer-duel claims the row by compare-and-swap and releases it in a catch, so an error during the accept puts the duel back to open and the player can retry.

Known gap That release only runs if the function lives long enough to run it. A hard death between the claim and the match insert (a timeout, an eviction) leaves the row accepted with a null answer_match_id, and nothing reopens it: sweepStaleMatches does not look at duels. The partial index duels_answer_idx makes the stuck rows cheap to find, so the sweep is a small addition. It is not written yet.

The deadline is seven days, not the eight minutes a match gets, because the two measure different things: a match deadline is how long a player has to play three scenarios, a duel's is how long somebody has to notice it. DUEL_TTL_MS lives in src/core/match/duels.ts rather than the Edge Function's shared module because the client draws the countdown too, and a deadline the two disagree about ends at the wrong moment on one of them.

A tournament fixture is a duel with a bracket around it

Tournaments are round-robin groups followed by a single-elimination bracket, and they add no new kind of match either. Each fixture is played as two legs, the way a duel is: whoever presses Play first gets the one-sided match send-duel would create, and once that settles the other player gets the contested match built from its frozen side. Submission, verification, settlement, forfeit and the clock are the ordinary paths.

What is new is one server-owned flag, matches.rated, false on every leg. settle-match and forfeitMatch write the verdict and move no rating when it is false, and find-match never offers an unrated side to the pool. The engine itself (src/core/tournament) is a pure reducer over one JSON document stored in tournaments.state and written back by compare-and-swap on revision through tournament_commit.

A settled leg, readpolicy.ts readLeg
leg 1 settled, scored      the fixture waits for leg 2
leg 1 void                 the attempt is void; the fixture replays
leg 2 win / loss / draw    settle-match's verdict from the leg-2 side
leg 2 loss, no score       forfeitMatch: the other player takes it
leg 2 void                 replay (a playoff draw replays too)

Results are never submitted. tournament_legs.ingested_at null marks a leg whose result has not been folded in, and every tournament request, plus settle-match and abandon-match on a leg, folds in whatever is outstanding. Nothing runs on a timer. tournament_open_leg reserves a leg with the tournament row locked and checks the fixture's attempt, the caller's place in it and the one-match rule in the same transaction.

Not in v1 No deadline or no-show timer: a player who never presses Play holds the round up until the host cancels. No host ruling or adjudication, so a stuck playoff fixture has no way to be awarded. Both are product decisions, not missing plumbing.

The clock only runs while nobody is playing

The deadline is an idle allowance, not a total. It is pushed forward every time a run lands, from the moment that run ended, so loading and playing cost nothing and only sitting in a menu spends it. A new match gets a longer first allowance for a cold start of Steam and the game.

Three minutes of idle, because once playing is free the only thing left to buy is the gap between scenarios — and a generous gap is what would let somebody stall to the last second of every round and turn a short match into a quarter of an hour of an opponent's time.

Quitting costs what running out costs

Pressing Abandon and letting the clock expire are the same act as far as the ladder is concerned, so they run through the same code and cost the same: a loss, at full weight. If only one of them were free, the free one would be the only one anybody used.

Two exceptions, both because nothing was contested. A seeding match has no opponent to lose to, and inventing a loss against nobody would be free rating tanking. A match whose runs are already in should be settled, not forfeited.

A crash is an absent round, not a bad one

Only the first attempt on each scenario counts, so an alt-F4 eight seconds in would otherwise become the attempt of record and settle as a loss. A run whose length falls below 90% of its scenario's known length is excluded rather than scored, which leaves the sides uneven and voids the match at zero rating weight.

Measured Scenario lengths are learned from real history, not hardcoded: the corpus has scenarios at 60s, 30s and 86s, and pressure and nevermiss scenarios end the moment you miss, so they get no fixed length and are never checked. Across 11,104 runs the rule flags 2, and 0 of the 675 runs on benchmark scenarios — the only ones a match is ever played on.

Timestamps are the sharp edge

KovaaK's writes a bare local wall clock into the filename and records no offset anywhere, so those digits are not a moment in time until somebody says where they were read. Two values want opposite things from them:

Duration is the gap between two local readings and is only right while both are in the same frame, so it is computed during the parse. played_at has to be a real instant comparable to a match window recorded in UTC, so the client sends its offset and the server rebuilds it. Getting this wrong rejected every run of the first real match as "outside the match window", six hours from where it belonged.

The security model

One rule, and everything else follows from it.

The rule

The client never computes anything that matters. It parses CSVs, hashes them, and uploads facts. Baselines, deltas, verification tiers and ratings are all computed server-side. A client that can write its own rating is a client that will.

Row-level security enforces it rather than convention:

  • Clients hold no write grant whatsoever on ratings, matches, match_sides, baselines or verified_pbs. Those are written only by Edge Functions using the service role, which bypasses RLS.
  • Runs are insert-and-read only — no update, no delete. History is append-only, so a bad run cannot be quietly removed after the fact.
  • runs.csv_sha256 is unique per player. That single constraint gives both idempotent backfill and replay protection: re-syncing is a no-op, and a good run cannot be submitted twice to win two matches.
  • The scenario a run belongs to is resolved by the server from the name. Letting a client nominate a scenario_id would let it file a run against whichever scenario flattered it most.

The two keys

The anon key is designed to be public and ships inside the desktop app. RLS is what protects the data, not the key. The service role key bypasses RLS entirely — anyone holding it can rewrite every rating in the database. It belongs only in Edge Function secrets on Supabase's servers, and the desktop build deliberately never even reads it.

Steam sign-in

Supabase has no native Steam provider and cannot have one: Steam speaks OpenID 2.0, which is not an OAuth2 flow at all. supabase/functions/steam-auth bridges the gap — it runs the OpenID dance, verifies the assertion with Steam directly, and only then mints a Supabase session.

Not skippable

Without that verification step, anyone could forge a callback naming any SteamID and take over that account. The SteamID is the join key to KovaaK's leaderboards, so a weak binding here would make every score check meaningless.

The desktop side uses the RFC 8252 loopback pattern: the app listens on an ephemeral 127.0.0.1 port, the browser handles login, and a single-use token — never a session — crosses back over loopback to be redeemed. The whole flow lives in the main process, so no token ever reaches the renderer.

Why core is separate

The Edge Functions import straight from src/core. Settlement, Glicko-2 and the integrity checks are therefore the same code the local suites exercise — there is no second implementation to drift out of sync. When the deploy log shows it uploading src/core/history/baseline.ts, that is the mechanism working.

Found, not designed

The most valuable parts of this system were found by measuring rather than decided up front.

KovaaK's serves the thresholds itself

The plan originally flagged the ~250 Voltaic score thresholds as a blocker needing a spreadsheet export. Chasing the evxl-link feature led through evxl's client bundle to where it gets the numbers — and evxl does not own them either. It reads KovaaK's own API. That one endpoint supplies official thresholds, rank names and colours for all 121 benchmarks, free.

Scores are a fixed multiple of a countable stat

Editing Score: and nothing else defeats every structural check — the file stays perfectly coherent. That looked unfixable locally. It is not: most scenarios score as a fixed multiple of something countable, and that multiple is a property of the scenario.

Learned from the corpusdata/score_models.json
VT Frogtagon Intermediate S5    score = kills    × 10
VT Aether Intermediate S5       score = hitCount × 1

219 scenarios modelled · 0% false positives · catches a +1% score edit

The sub-skill mapping was wrong until it came from the source

The nine Voltaic sub-categories were first derived by reading scenario descriptions. That produced a plausible, confident answer that was wrong on 6 of 18 scenarios — Tracking's Precise and Reactive groups were swapped wholesale. The nine names were guessed correctly, which is exactly what made the wrong groupings easy to believe. Only going to Voltaic's own published spreadsheet settled it.

The pool now draws from twenty-three benchmarks rather than Voltaic alone, and Voltaic's sheet can only classify Voltaic's eighteen. So the sub-skills are derived instead from the category names every benchmark publishes for its own scenarios — normalised for case and spacing, and keyed by KovaaK's aim type so that "Micro" can mean the clicking sub-skill in Lemon Static and precise tracking in Astro without either being special-cased. Still nothing read from a description.

Where KovaaK's has no aim type at all — about a hundred scenarios — the category comes from the author's own word: “Evasive Switch” is a key in the Switching table and nowhere else, so an author using it has said Switching. A word that two of the three tables claim is refused rather than guessed at. The first version voted inside the box instead — a benchmark's category slot in one difficulty looks homogeneous by construction — and was confidently wrong: Viscose files domiSwitch and tamTargetSwitch Smooth both under “Evasive”, one clicking and one target switching, so the vote put a target-switching scenario into Linear Clicking with a 51,457-entry board behind it. Same shape as the description-reading mistake, one level down.

What makes that trustable is that the earlier mistake is now a test. Voltaic's scenarios go through the same normalisation as everybody else's, and Voltaic published where they belong, so the derivation has to land where Voltaic says it does — on all 106 of them. It does, and npm run build:subskills fails if it ever stops. Eleven sub-skills come out: Voltaic's nine, plus Micro Clicking (named by eight benchmarks) and Reading Tracking (seven). They are named in two words the way snakbox, Avasive and wobin name them, because “Micro” and “Speed” mean different things in different categories and one word cannot say which.

Bugs and lessons

Each of these cost real time. They are grouped by the lesson rather than the symptom, because the lesson is what applies next time.

Measure a check before you let it reject anything

First-draft integrity checks, run against 11,058 genuine runsnpm run validate:verify
CheckFalse positivesWhat was actually true
reject TTK < 20ms 62.0% KovaaK's TTK is first-hit-to-kill within a burst, not reaction time. Sub-millisecond is routine.
reject negative scores 3 runs Pressure scenarios subtract for misses. Real runs score −500.
one row per kill, numbered from 1 0.85% Kill # is a running counter. Penalty rows repeat it, multi-kills skip it, numbering starts at 0 or 1.

A 62% false-positive rate would have accused two-thirds of honest players. Final state: every hard check sits at 0.00% across the whole corpus, and anything that could not reach zero was demoted to advisory rather than kept.

Fix it in every place, not the first place

The negative-score lesson was learned once, applied to the verification code, and not applied to the database constraint. Months of understanding lived in a code comment naming the exact three runs, while check (score >= 0) sat in the schema waiting. The backfill failed on batch 5 — the one batch containing a pressure run.

A warning you have written off twice is worth reading

The dead sign-in button

Electron 33 bundles Node 20, which has no native WebSocket. supabase-js needs one and throws on startup, so createClient died before sign-in could do anything. The deprecation warning had been visible in the build output for two sessions and dismissed as cosmetic both times. Upgrading to Electron 38 (Node 22) fixed it at the root.

Punctuation can be load-bearing

Three separate scripted attempts to normalise punctuation produced worse text: a parenthetical mangled across a line break, pairing that reached across table rows, and a quest whose separator was carrying meaning — "1140 takes you to Jade — 10 more" became "Jade 10 more". Rules cannot tell an appositive from a comma splice. The fix that worked was reading every instance and writing each replacement by hand.

Normalisation can create a catch-all

A benchmark-name normaliser stripped everything outside [a-z0-9], which reduced the registry's Chinese-named entry to an empty string. Since every string starts with "", that entry then matched any unknown input — so a typo silently tracked a benchmark the player had never heard of.

Running and maintaining it

What to type, in what order, and the handful of things that will bite you if nobody wrote them down.

The daily loop

Working on itno backend needed
npm start            build the client and launch it
npm run dev          the same, rebuilt and relaunched on every save
npm run doctor       why is it not working: bundle, folder, keys, data
npm run smoke        boot headlessly and check it renders — no window
npm run typecheck    tsc, no emit
npm run validate     every suite, against real runs
npm run ui           regenerate the shareable single-file preview

npm start runs build:app first. That matters more than it sounds — see the trap below.

npm run dev is the same build, watched: esbuild rebuilds whatever the main process reaches, the renderer and preload are copied on save, and the window is relaunched — which is the part that cannot be skipped, since a running window keeps the bundle it started with. A build error leaves the window up on the last good build rather than closing what you were looking at. Closing the window ends the loop.

npm run doctor answers the question that usually gets asked an hour late: is the bundle older than a source file, is there a stats folder and how many runs are in it, are the client keys set, how old is the benchmark registry, does the season still parse. It exits non-zero only for something genuinely broken.

Deploying

Order is not arbitrary. The sync writes to columns the migration creates, and the functions read what the sync wrote.

In this orderafter a schema or function change
npx supabase db push --yes    migrations
npm run sync:reference        score models, world records, durations
npm run deploy:functions      every Edge Function
npm run verify:deployment     prove it against the live project

Learned the hard way deploy:functions deploys every function every time, deliberately. It once listed four of five, and the missing one sat on a stale bundle for weeks with nothing to indicate it. If you add a function, add it to that script and to the anonymous-caller checks in verifyDeployment in the same commit.

WARNING: Docker is not running during a deploy is noise. Docker is only needed for the local stack, never for deploying.

Editing a season

Season workflowadmin only
npm run grant:admin -- <steamId> --note "why"   once, per admin
npm run grant:admin -- --list                   who has it

npm run build:season    rebuild season 1 from tools/season/design.ts
npm run push:season     load it into the project as a draft
npm run validate:season prove edits keep the ladders in step

Day to day you will not use those. The Season tab in the app is the editor: rank names, colours, per-scenario thresholds, category energy, adding and removing both scenarios and ranks. Saving writes the file and rebuilds, so a change is visible immediately.

There is deliberately no in-app path to granting admin. The admins table has no client write policy at all, so the service-role key is the only door — which is the right home for the power to decide what a rank means.

Not a security boundary The admin gate hides a tab. The season is a file on the machine and anybody sitting at it can open the JSON in a text editor. The gate matters the day a season is published to other people, not before.

The trap: two copies of data/

The app points the core at dist/data, and build:app rewrites that directory from data/ on every build. Anything written back to the runtime copy therefore survives exactly until the next build and then vanishes with nothing to say it had.

Saving a season writes both — the runtime copy so the change shows now, the source so it is still there tomorrow — and reports how many files it wrote. If a save ever says 1 file on a dev machine, the source lookup failed and the edit is living on borrowed time.

Before letting anyone else in

Not done yet

Stated plainly, so nothing here reads as finished when it is not.

  • No contested match has been played. The loop works end to end — a seeding match has been queued, played, verified and settled, and its run set is in the pool. What has not happened is a match with somebody on the other side, so the win/loss path and the rating change have never run against a real opponent.
  • Ratings are still one per player, not six. The season splits the six categories into separate ladders for grading, but ratings is keyed on player_id alone, so "my Precise Tracking rank" has no answer yet. Splitting it is the next real piece of PLAN.md §14.
  • Season rollover is not built. Season 1's thresholds are seeded from Voltaic's numbers. The step that makes seasons worth having — deriving season n's thresholds from season n−1's population — needs a population first.
  • Score models cover 18 of 248 scenarios server-side. They are learned from observed runs, and the seed corpus is one player's history. Coverage grows on its own as people upload; scenarios without a model skip that check rather than failing it.
  • Quest XP is stored locally and is not server-validated. Deliberate for now — XP is cosmetic and never touches rating, so editing that file only cheats you. If XP ever becomes visible to others it must move server-side; the quests table already exists for that.
  • Hardware cheats are invisible to this design. An aimbot producing genuine KovaaK's scores passes every check, because KovaaK's itself accepts them. Mitigation is statistical review at the top ranks, which is where every competitive game lands. Better said publicly than oversold.
  • Live matchmaking is written but unexercised. Starvation-free across four simulated populations, but no real queue has ever run.
  • No installer, and no code signing. An unsigned Windows binary throws a SmartScreen warning that looks alarming to a stranger.
